📌Link to the lab -> [https://cyberdefenders.org/blueteam-ctf-challenges/ulysses/]

### 📓 Scenario:
A research server was flagged for suspicious activity after multiple failed authentication attempts. Analysts detected a brute-force attack, unauthorized outbound connections, and possible persistence mechanisms. Using Volatility,
a custom Debian5_26 profile was loaded to analyze memory dumps and identify malicious processes. Your task is to investigate forensic artifacts, determine the attacker's entry point, and uncover any deployed payloads.

The image verifies the Volatility profile integration and displays the initial process list from the compromised system.

#### ❔  1: The attacker was performing a Brute Force attack. What account triggered the alert?

$${\color{purple}__Identification\space of\space the\space Targeted\space Account\space During\space SSH\space Brute-Force\space Activity__}$$

$${\color{red}__Analysis__}$$

To determine the account targeted during the suspected brute-force attack, authentication logs were examined using FTK Imager. Since brute-force attacks rely on repeated authentication attempts against user accounts, system logs containing SSH authentication events provide valuable evidence regarding the attacker's actions and intended target.

The investigation focused on the /var/log/auth.log file, which records authentication-related events generated by the SSH daemon (sshd). Analysis of the log entries revealed a high volume of failed login attempts originating from the IP address 192.168.56.1. Multiple entries contained messages such as "Invalid user ulysses" and "Failed password for invalid user _ulysses_", indicating that the attacker repeatedly attempted to authenticate using the account name ulysses.

The timestamps show numerous consecutive authentication failures occurring within a short period, which is consistent with automated password-guessing activity. The repeated use of the same username across multiple connection attempts demonstrates that the account name was the primary target of the brute-force attack.

$${\color{yellow}__Evidence \space Interpretation__}$$

The authentication logs provide direct evidence that the attacker targeted the ulysses account during the brute-force campaign. The repeated SSH login attempts against this username, combined with continuous password failures from the same source IP address, indicate a systematic effort to gain unauthorized access through credential guessing.

The fact that the system reports "Invalid user ulysses" suggests that the account either did not exist at the time of the attack or was incorrectly identified by the attacker. Nevertheless, the logs clearly establish that ulysses was the account name used throughout the brute-force activity and therefore triggered the security alert.

#### ❔  4: What is the victim's IP address?

$${\color{purple}__Identification\space of\space the\space Victim\space Host\space IP\space Address\space Through\space Memory\space -\space Based\space Network\space Analysis__}$$
$${\color{red}__Analysis__}$$

To identify the IP address assigned to the compromised server, network connection artifacts were extracted from the memory image using the Volatility Framework's linux_netstat plugin. Unlike disk-based analysis, memory forensics provides visibility into active and recently established network connections present at the time the memory acquisition was performed.

The linux_netstat plugin enumerates network sockets and associates them with running processes, allowing investigators to identify listening services, active connections, and communication endpoints. Examination of the output revealed several network connections involving the IP address 192.168.56.102. Notably, connections were observed between _192.168.56.102_ and _192.168.56.1_, including established sessions associated with the processes _sh (PID 2065) and nc (PID 2169)_.

Because _192.168.56.102_ appears as the local endpoint in multiple connections and hosts services listening on common ports such as SSH (22) and SMTP (25), it can be identified as the IP address assigned to the compromised system. The remote system, 192.168.56.1, represents an external host communicating with the victim server.

$${\color{yellow}__Evidence\space Interpretation__}$$

The memory-resident network artifacts clearly indicate that _192.168.56.102_ is the victim machine's IP address. This conclusion is supported by the fact that the address is consistently associated with local services and serves as the source endpoint for established network connections.

The observed communication between 192.168.56.102 and 192.168.56.1 is particularly significant because it suggests interaction between the compromised host and another system on the network. The association of these connections with shell (sh) and Netcat (nc) processes may indicate post-compromise activity, potentially involving remote command execution or attacker-controlled communications. These findings warrant further investigation into the related processes and connection history.

#### ❔  8: What is the CVE number of exploited vulnerability?

$${\color{purple}__Identification\space of\space the\space Exim4\space Vulnerability\space Leveraged\space During\space the\space Compromise__}$$
$${\color{red}__Analysis__}$$

After determining that the Exim4 SMTP service was the likely attack vector, additional examination was conducted to identify the specific vulnerability exploited by the attacker. Using FTK Imager, the Exim4 mainlog file located in /var/log/exim4 was reviewed to obtain version information about the mail service running on the compromised server.

The log entries revealed that the server was running: exim 4.69 daemon started

This version information was particularly significant because the target system was previously identified as Debian GNU/Linux 5.0 (Lenny). Correlating the Exim version with publicly available vulnerability advisories and Debian security bulletins revealed that Exim versions prior to 4.70 were affected by CVE-2010-4344.

According to Debian Security Advisory DSA-2131-1, CVE-2010-4344 is a heap-based buffer overflow vulnerability in Exim's string_vformat() function. The flaw allows a remote attacker to execute arbitrary code through specially crafted SMTP messages containing malicious headers. Successful exploitation may result in unauthorized command execution under the privileges of the Exim process.

This vulnerability aligns with other evidence collected during the investigation, including malicious SMTP transactions, command injection attempts recorded in Exim logs, and the subsequent execution of payloads that established outbound communications with attacker-controlled infrastructure.

$${\color{yellow}__Evidence \space Interpretation__}$$

The evidence strongly suggests that the attackers exploited _CVE-2010-4344_ to gain access to the server. The determination is based on three key observations:

1. The compromised host was running Exim version 4.69, as confirmed by the Exim mainlog.
2. Exim 4.69 is documented as vulnerable to _CVE-2010-4344_.
3. Exim logs contain malicious SMTP traffic and command execution attempts consistent with exploitation of an Exim remote code execution vulnerability.

The attack chain observed during the investigation indicates that the SMTP service was targeted, malicious commands were injected through SMTP interactions, and payloads were subsequently downloaded and executed. These findings are consistent with known exploitation techniques associated with vulnerable Exim deployments.

#### ❔  11: Which port did the attacker try to block on the firewall?

$${\color{purple}__Identification\space of\space the\space Firewall\space Port\space Blocked\space by\space the\space Attacker's\space Persistence\space Script__}$$
$${\color{red}__Analysis__}$$

To determine which port the attacker attempted to block on the compromised system, the investigation focused on artifacts previously identified as malicious payloads downloaded during the intrusion. Earlier analysis of the Exim4 logs revealed that the attacker downloaded the archive rk.tar, which was subsequently located within the /tmp directory using FTK Imager.

Inspection of the extracted archive contents revealed several suspicious files commonly associated with post-exploitation toolkits and persistence mechanisms, including:

- dropbear
- install.sh
- mig
- vars.sh

The installation script (install.sh) was examined using a text editor to identify any system modifications performed by the malware. Within the script, commands were found that established persistence through /etc/init.d/boot.local and modified local firewall rules using iptables.

The following command was present in the script: /usr/sbin/iptables -I OUTPUT 1 -p tcp --dport 45295 -j DROP

This command inserts a firewall rule at the top of the OUTPUT chain, causing all outbound TCP traffic destined for port _45295_ to be dropped. The presence of this command indicates that the attacker intentionally attempted to block communications over this port.

$${\color{yellow}__Evidence \space Interpretation__}$$

The recovered installation script provides direct evidence that the attacker attempted to block TCP port _45295_ through a persistent firewall rule. Because the rule is written into the system's startup configuration (/etc/init.d/boot.local), it would remain active after system reboots, demonstrating an effort to maintain long-term control over network behavior.

From an investigative perspective, this action suggests the attacker was attempting to either suppress legitimate network communications, interfere with administrative access, disable competing services, or conceal malicious activity occurring on the host.
